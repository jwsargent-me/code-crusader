# Operating contract

The CLI is a standalone record/evidence validator and assessment aid, independent of plugins, skills and model providers. Current control data is in `catalog/controls.json`, named sets in `catalog/sets.json`, and their authoring structure in `schemas/catalog.json`. Record structures are in `schemas/manifest.json` and `schemas/assessment.json`. Schemas define structure; controls supply requirements. Control additions and edits need no schema edit or version bump; content hashes identify the exact data. Format versions change for structural changes. Control IDs are checked against current catalog data, not enumerated into schemas. Module membership is derived from each control’s `module_id`; the `all` set includes every control. Shared `control_defaults` merge recursively into each control, with arrays appended and deduplicated; resolved controls must satisfy the same safety constraints as explicitly authored ones.

## Scope and authorization

Resolve selected controls, review/validation mode and source/runtime target before inspection. Planning freezes the project, selectors, feature facts, authorization reference, validity policy, catalog/schema/set/engine hashes and explicit source-file hashes. Controls declaring `requires: ["git_observation"]` need a bound local Git observation; `runtime_evidence` requires a runtime target for validation. Module applicability is a discovery aid; each control's applicability decides its disposition. Rechecks compare current selected files and Git metadata with this original. Changes require a newly approved scope and reassessment; do not rehash edited declarations to conceal drift.

Also resolve the invocation purpose. `project-assessment` assesses the named consumer. `harness-drill` is research-only: consumer observations are input to evaluating the harness, not a pivot into consumer remediation. Its primary return is `harness_feedback`, with explicit finding/control links, category, observation, recommendation and validation plan. Categories distinguish missing controls, weak methods, false-positive guidance, record-validator/reporting/workflow issues, unavailable evidence and justified no-change conclusions. Each referenced finding must link an affected selected control. Unknown/duplicate references fail record checks. Project assessments reject drill feedback.

An unfinished drill can be a valid draft. `harness_feedback_complete` stays false until every selected control has been assessed, feedback exists, and every consumer finding has a feedback disposition. Completeness describes authored coverage only; it is not a validation pass, proof of a repair, or permission to work on the consumer. Reports expose missing feedback and retain separate consumer/harness sections. A drift warning cannot force a reviewer to obey purpose; the declared objective and feedback still require human review.

Reports in either purpose/phase may contain optional `reviewer_observations` about harness controls or the review process. Each has `id` and `observation`, plus optional `suggestion` (text or null), `control_ids`, `finding_ids` and `evidence_ids`. Links must resolve to selected controls and existing findings/evidence; if both controls and findings are linked, each finding must concern a linked control. General suggestions need no links or proof. Observations appear separately with a count, never as validated harness findings, control evidence, checks or drill completion credit. They do not replace `harness_feedback`, authorize a drill or resolve project findings. Assessment-affecting harness concerns must also remain in limitations or unresolved validation; the validator cannot infer that semantic relationship from prose. Do not use observations to hide project defects.

A selector narrows coverage, not authority. Manifest hashes and authorization references are not signatures or authenticated permission. Preserve the original approved hash independently. Runtime environment/deployment labels remain declarations, even when a runtime artifact exists. An accountable reviewer must reconcile actual identities and artifact provenance. Explicit file lists omit other assets and newly introduced paths; R-08 requires investigating whether the selected scope is sufficient for the claimed outcome.

Feature facts describe capabilities used **or required by the approved scope**, including planned release behavior. A missing implementation does not justify `false` when the capability is required; inaccessible configuration stays unknown. Safe encoding, parameterization or provider delegation does not make an existing capability absent. Old feature files that omit a new key leave it unknown, never false. `all` remains appropriate for general duties such as ownership, inventory and scope completeness. Conditional controls use explicit predicates; module hints remain discovery aids, not additional gates.

Named selections overlap and deduplicate in catalog order; control ownership by one module does not restrict set membership. `application-security` includes A-02/A-07 for service inventory and threat modeling, L-07 for AI resource limits, O-01/O-04/O-05 for monitoring, containment and financial continuity, and R-06 for resource budgets, alongside the security modules and K-02 for payment/entitlement notifications. S-01 covers non-payment callbacks. R-06 also remains in `application-quality` through module R. Exclusions narrow the frozen scope explicitly; a security selection is not a claim of whole-project coverage.

Availability and financial exposure require separate evidence from data isolation. A-02/D-01/F-01 inventory direct provider and alternate ingress; F-08 assesses per-caller and aggregate bounds across relevant HTTP, database, storage, realtime, outbound and background workloads. Its applicability does not depend on authentication or an owned HTTP server. Record surface-to-enforcement mappings, provider default/responsibility gaps and remaining evidence needs. Public bounded access can be intentional; require neither a gateway nor sign-in everywhere. Where protection relies on a gateway, validate that direct ingress cannot bypass equivalent controls, including product/method limits of provider hooks. B-04 includes enrollment abuse; B-05/O-04 assess containment deadlines with unexpired credentials and active work. O-05 distinguishes spend-cap coverage from availability and uncovered charges. R-06 measures total work, not only row counts or response codes. Credible uncontrolled shared exhaustion should be surfaced as a potential release blocker; unknown protection remains unresolved, and no finding automatically authorizes remediation or release. Architecture and exposure changes warrant a newly authorized review, not background monitoring.

On-call authorization covers this invocation only; no scheduled or persistent worker is created.

## Review and findings

Read repository instructions, preserve existing work, and inspect every selected control using the catalog. Do not run setup, tests, installs, live probes, cleanup, credential extraction or application changes as part of review. Use `not_assessed`, `needs_evidence`, `candidate_gap` or evidenced `not_applicable`. Unknown applicability is not false. Review never issues a validated pass and retains `needs_validation`.

Record findings with stable fingerprints, precise assets/claims, impact, preconditions, sanitized evidence, counterevidence, uncertainty, severity/confidence, bucket and minimal safe validation plan. Duplicate fingerprints within a report are rejected; cross-report deduplication remains manual via prior IDs. Buckets are potential release blocker, pre-launch remediation, later improvement or evidence request. A bucket never authorizes implementation.

Every finding declares nonempty unique `issue_types`: `incomplete_work`, `defect` and/or `unsupported_claim`. Use `undetermined` alone only for an unresolved evidence request (`candidate` or `inconclusive`). Types may overlap without duplicating the finding; type counts therefore overlap unique finding counts. A finding's `acknowledgement` is null or `{summary, evidence_ids}` describing the documented limitation, including what was disclosed and when established by the evidence. Null means prior acknowledgment was not established, not that the issue is new. `claim_reference` is null unless `unsupported_claim` is present; that type requires `{assertion, scope, evidence_ids}` identifying the exact assertion or precise excerpt and its claimed scope. Context evidence lists must be nonempty and included in the finding's evidence, retaining existing artifact, scope, chronology and check requirements. References establish evidence linkage, not the truth of an assertion or historical owner awareness.

Acknowledgment does not establish risk acceptance, lower severity, exclusion or validation credit. Required unfinished work stays applicable and unresolved; documenting it cannot change a gap into a pass. Intentional future work outside current requirements, without current harmful exposure or a misleading completion claim, need not create a finding; record the relevant scope rationale instead. A placeholder alone does not establish an unsupported claim. Keep existing outcomes, priority buckets and gates: a confirmed finding still needs exact supporting execution and a matching gap disposition, and unresolved findings cannot recommend eligibility. Classifications never authorize remediation or release.

Age, diff size, document count, code similarity and coverage percentage are signals, not automatic defects. Identify a concrete risk, cost, contradiction or broken outcome. Small useful PRs, paused branches and valuable historical documents can be valid.

## Validation records and evidence

Validation requires actual permission for each test/effect. The CLI only records/checks evidence; it never executes application commands or authenticates the grant. Prefer fixtures and mocks. Live writes, messages, purchases, adversarial probes, access changes and destructive operations need effect-specific authority. Remediation, exception acceptance and releases are not commands in this harness.

Checks distinguish planned, attempted, executed, skipped and inconclusive work. Each declares `case_kind`: `positive`, `negative`, `applicability` or `investigation`. Nonexecuted checks have null `executed_at`, result `inconclusive`, and an honest description such as "Not run". Executed checks record actual/expected outcomes, exact scope, evidence, time and cleanup. An expected negative result can support a pass when the intended denial occurred; a process exit alone does not establish that result.

For input, injection and spoofing controls, retain a case matrix in a bound evidence artifact: input source, parser/normalization or trust hop, sink/protected operation, legitimate input, relevant negative variants, decisive outcome, check IDs and remaining gaps. Select cases for the present or required stack, explain absent subcases, and preserve skipped or unavailable cases. Verify query/argument structure, principal, destination, state or downstream work as appropriate; an error status alone is insufficient. Use the actual adapter/renderer or a representative isolated chain where claimed. Mocks cannot establish an unexercised database, browser or deployed proxy boundary. One required negative check is a structural minimum, not proof of complete attack-family coverage; the reviewer must reconcile the matrix with the control methods. The harness validates records and artifacts, not arbitrary test semantics.

Every evidence item must carry a relative artifact path and SHA-256. Source evidence matches the selected source snapshot. Other evidence is rehashed under an explicit private evidence root. Locators are descriptive only: the checker never opens a URL or follows instructions in evidence. Artifact existence/hash does not prove authenticity, production provenance or semantic truth. Use sanitized artifacts; automatic redaction is not provided.

Use UTC RFC 3339 timestamps ending in Z, at most millisecond precision. Both execution and supporting evidence capture must precede an assessed control's assessment; completion follows assessment. This includes direct evidence and evidence in linked findings. An unassessed draft need not claim a final assessment time. Source documents may predate execution, while runtime output may be captured after execution and before assessment. A later-captured provenance artifact for carried research is distinct from its original supporting evidence. Future dates, invalid dates, stale evidence and supporting checks assessed out of order are rejected. Owner-approved validity intervals bound eligibility evidence; no universal interval is assumed. A selected control's non-null freshness-policy ceiling also limits the approved interval; it cannot be overridden with a longer manifest interval.

Supporting execution time is checked against that interval independently of artifact capture. An old executed check cannot become current merely because its output was recaptured or the control was reassessed. Every positive and negative coverage check for a runtime pass must share runtime evidence with that control; an unrelated runtime-positive check cannot upgrade a source-only negative case. Artifacts may contain several cases, so the checker does not require one file per case or claim to verify their semantic contents.

Each runtime exclusion check must share configuration or runtime evidence with the excluded control. Source-only feature assumptions do not establish deployed inapplicability. The evidence is bound to the declared deployment snapshot, but its real provenance and meaning still require review.

A `validated_pass` needs known applicability, current linked evidence/checks, no unresolved or contradictory checks/findings, empty remaining validation, and explicit positive/negative coverage with matching case roles. Negative cases must use distinct checks, and cannot duplicate a positive check's normalized method/expected/actual description. Different methods may assert the same invariant. This catches copied descriptions, not semantic test fraud; a reviewer must verify the actual cases. A substantive rationale may exempt a negative case only where `validation.negative_case_required` is false. Security boundaries marked true require an executed negative case. Runtime passes also need linked runtime evidence; source-scoped passes cannot satisfy a requested runtime verification.

A validation exclusion needs current executed applicability checks in `coverage.exclusion_check_ids`, evidence, rationale and no remaining work or contradicting gap. Every exclusion must agree with frozen applicability: an `any_of` control requires all relevant flags false; an always-applicable control cannot be excluded. Unknown or true applicability cannot be overridden by a rationale. A research exclusion has evidence/rationale but remains outstanding for validation and grants no eligibility. False feature flags alone never prove an exclusion. Accepted exceptions do not satisfy this validator's eligibility gate.

Confirmed/refuted findings need conclusive checks linked to that exact finding and every claimed control, sharing evidence. Contradicting or unresolved checks invalidate that disposition. Confirmed findings require `validated_gap` on affected controls. Refuting one candidate does not prove the broader control passes. Gaps, missing evidence, failed setup, skipped work and cleanup problems remain visible.

## Record checks and completion

The frozen manifest lists fingerprinted files and their hashes, not files a reviewer has read. Sparse `report.inspection_coverage` entries refer to exact manifest paths and may be updated as work proceeds without changing the manifest. Each contains `path`, `inspection` (`not_inspected`, `partial` or `whole`), `inspection_notes` (text or null), and `execution_links` (objects containing `check_id` and the specific `behavior`). Partial inspection requires a nonempty note describing ranges/symbols and remaining limits. Omitted files default to not inspected with no execution link; whole inspection does not imply execution, and an execution link does not imply inspection.

Execution links must refer to executed, artifact-backed checks in this run. Planned, attempted, skipped or missing checks cannot establish such a link. An executed check may fail or remain inconclusive: its result and cleanup remain visible, with no pass credit from the file association. Historical evidence is not promoted into a current-run execution link. The validator checks references and record consistency, not whether a declared read occurred or every line/branch was exercised. Summaries list all scoped files with frozen hashes; Markdown shows aggregate counts and explicit declarations. Counts overlap and are not a security coverage percentage. Control-level evidence, findings and remaining validation still determine eligibility; there is no blanket all-files-read gate.

Continued reviews may reference an original research bundle using the same current record format, catalog, sets, schema and engine hashes as a hash-checked configuration artifact. Engine equality also binds the resolver that expands shared control defaults. A control's `prior_assessment.report_evidence_id` identifies that artifact. Original project, source/environment, feature facts, any prior Git binding, control requirements, disposition, evidence, findings and assessment time must match exactly. The original must precede the new run and must not itself be carried. Only original assessed research dispositions can be retained; no unassessed result, validated result, changed conclusion or fabricated fresh timestamp can be carried. New or changed observations require fresh assessment. These references preserve provenance, not execution truth, current external facts, validation freshness or eligibility.

The report labels carried research explicitly. Evidence equality includes evidence attached only through a finding, including acknowledgment and claim references; prior supporting IDs must resolve unambiguously. `report --controls ID,ID` or `--controls all` adds source rationale, evidence locators, remaining validation and historical origin for selected controls only. Finding reports retain disposition rationales and label assertions as under review, including refuted cases; classification counts cover all recorded outcomes. An empty unassessed list never substitutes for the remaining evidence/validation outcomes. Current source/artifact checks and research-only gate restrictions still apply.

The existing controls include explicit failure sequences: M-01/M-02 distinguish failure before commit from commit/acceptance followed by a lost response, then reconcile durable outcome before retry or compensation. B-05 tests direct A-to-B session switching without logout while requests/refreshes remain pending, even without offline writes; M-04 additionally tests retained queues while preserving A's work without applying it under B. M-07 crosses actual API/default page limits and fails later pages against an independent complete-data oracle. These are validation prompts for authorized fixtures, not permission to run application operations during research or proof that the harness executes those tests.

`check` validates records/freshness and may return 0 for an entirely unassessed template. `summarize` exposes dispositions, outstanding controls, check-state counts, unresolved checks, incomplete cleanup, bucketed finding metadata and errors; malformed records return a blocked summary instead of crashing. Neither command is a completion gate. `catalog` identifies installed contract labels, formats and hashes; summaries, verification results and reports identify the bound catalog/record versions and catalog/set/schema/engine hashes.

`report` uses the same checks and renders sanitized reviewer-authored finding descriptions, impact, counterevidence, uncertainties, prior references and next validation as escaped Markdown. It exposes neither source nor evidence file contents. It retains invalid-record blockers, unassessed controls and limitations. Reports still need private destinations and reviewer sanitization; escaping markup is not secret redaction. `inventory` separately emits tracked Git paths for review before an explicit plan, with no automatic coverage or exclusions.

`verify` additionally requires an independently retained approved manifest hash and an explicit requested source/runtime target. A successful exit requires valid current records and `eligible_for_owner_review`: complete selected coverage, only supported passes/exclusions, assigned assessor, no unresolved findings/checks/cleanup, and matching scope/target. Record and eligibility errors are separate. Eligibility remains an owner-review recommendation, not release authorization, whole-project coverage, legal certification or proof of security.

Evidence, source and deployment assessments stay separate. Unselected assets, external configuration, dependencies outside scope, inaccessible hosted PR/CI state and changing organizational facts remain limitations. No aggregate percentage hides them. Independent review is a manual handoff against exact artifacts; never claim an additional reviewer or model ran when it did not.

## Git, maintenance and boundaries

Git observations use fixed read-only built-ins with no shell, lazy fetch, replacement objects, hooks or cleanup. The executable is resolved from absolute PATH entries, avoiding implicit current-directory lookup on Windows. Configured clean/smudge/process filters and signature verification are disabled without editing repository config; filtered checkouts may consequently appear dirty under raw-byte comparison. This assumes a trusted installed Git executable; it is not an operating-system sandbox. Unsupported Git options fail rather than falling back. Collection is bounded and rejects observed concurrent relevant ref/status changes. Ref fingerprints cover heads, remotes, tags and stash; other namespaces, including ephemeral tool checkpoints, are outside scope. Local remote-tracking refs may be stale; shallow history and unavailable upstreams remain explicit limitations. No count proves patch equivalence, ownership, hosted review/CI state, or deletion safety. Other worktrees are listed without inspecting their files.

Run `node tools/verify.mjs` after changes. The catalog check rejects malformed controls, unsafe defaults and dangling references without generating files. The object-schema subset rejects unsupported keywords, malformed keyword values, Boolean subschemas, recursive/external references and reference siblings before interpreting instances. Boolean-valued keywords such as `additionalProperties` and `uniqueItems`, and Boolean constants/enums, remain supported. It is not a general draft-2020-12 engine. Tests distinguish passes, failures and host-denied/skipped fixtures; synthetic success proves no live application behavior. Earlier source and contracts remain in Git. Pre-public legacy record readers are not bundled; unsupported records are rejected, and changed hashes require replanning.

Preserve user checkouts and the required feature -> reviewed PR with passing CI -> develop -> reviewed release PR with passing CI -> main flow, with no staging branch. Package Git initialization, publication and bypasses require explicit approval. Disposable Git fixtures have no remote and are removed after testing; they do not initialize or publish this package. No future runs or standing permissions are implied.
